# 담당자(현업) 질문 은행

원칙: 해법 단어(AI·자동화·대시보드)를 먼저 꺼내지 않는다 · **한 메시지에 질문 1~2개** · 숫자로 받는다 · 합의는 글로 확인받는다.
순서: 사건 → 지금 방식 → 숫자 → 사용자 → 데이터 → 경계 → 믿음.

| 단계 | 질문 | 얻는 것 |
|---|---|---|
| 사건 | 이 문제가 실제로 터진 최근 사례 하나만 말씀해 주시겠어요? (언제·어떤 대상) | 검증 기준점 |
| 사건 | 문제가 시작된 무렵 바뀐 게 있었나요? (장비·레시피·정비·인력·시스템·제품 구성) | 변화점 가설 |
| 지금 방식 | 지금은 이걸 어떻게 처리하세요? 기준이 있나요? | 기준선 |
| 지금 방식 | 지금 방식에서 가장 불편하거나 자주 틀리는 부분은요? | 진짜 병목 |
| 숫자 | 하루/주에 몇 건, 한 건에 몇 분, 놓치면 어느 정도 손해인가요? | 성공 기준 단위 |
| 숫자 | 놓치는 것과 잘못 알리는 것 중 어느 쪽이 더 곤란한가요? 하루 몇 건까지면 보시나요? | 임계값 근거 |
| 사용자 | 결과는 누가, 언제, 무엇을 결정하려고 보나요? | 산출물 형식 |
| 사용자 | 그분들이 결과를 믿으려면 무엇이 함께 보여야 하나요? | 설명 가능성 |
| 데이터 | <열 이름>은 정확히 무슨 뜻인가요? 같은 대상이 여러 번 나오는 이유는요? | 중복·재처리 규칙 |
| 데이터 | -1, 0, 빈칸 같은 값은 무슨 뜻인가요? | 센티넬 |
| 데이터 | 이 값은 언제 채워지나요? 판단 시점에 알 수 있는 값인가요? | 누수 |
| 데이터 | 시간은 어느 시간대 기준인가요? 데이터는 얼마나 자주 들어오나요? | 시간 정렬·갱신 |
| 데이터 | 그룹(제품·장비 등)마다 평소 값이 다른가요? | 층별 기준선 |
| 데이터 | 최근 장비·시스템 쪽 이슈가 있었나요? | 숨은 교란 요인 |
| 경계 | 어디서 돌아가나요? 인터넷·설치가 되는 환경인가요? | 기술 제약 |
| 경계 | 데이터를 밖으로 보내면 안 되는 등 꼭 지켜야 할 것이 있나요? | 보안 |
| 경계 | 이번에 하지 않아도 되는 것은요? | 범위 |
| 경계 | 나중에 누가 유지보수하나요? | 문서·구조 |
| 믿음 | 원인을 짐작하시는 게 있나요? 그렇게 보신 근거는요? | 검증할 가설 |
| 마무리 | 오늘 결과가 "성공"이려면 어떤 숫자가 어떻게 되면 될까요? | 합의된 성공 기준 |

## 서면 합의 템플릿
```
지금까지 말씀을 이렇게 이해했습니다. 틀린 부분 고쳐 주세요.
1. 문제:
2. 원인 가설:
3. 성공 기준:
4. 만들 것 / 안 만들 것:
5. 제약:
이대로 진행해도 될까요?
```

## 수용 확인 템플릿
```
지금 결과입니다: <핵심 숫자 2~3개>. 기존 방식으로는 <비교 숫자>였습니다.
이걸로 <결정 상황>에서 바로 쓰실 수 있을까요? 빠진 게 있으면 말씀해 주세요.
```
